## Fire-TV-Installationsfehler: Ursachen + Gegenprobe (29.10., Abend)
- Fehlermeldung „beim parsen des pakets ist ein problem aufgetreten" = `INSTALL_PARSE_FAILED`, also **minSdk**, nicht ABI.
  Gerät: Fire TV Stick 4K 1. Gen, Fire OS 6.7.1.1 = Android 7.1.2 = **API 25**; APK hatte `minSdk 28`.
- Zweiter, unabhängiger Blocker: APK enthielt nur `arm64-v8a`. Fire-TV-Sticks laufen meist mit 32-Bit-Userspace
  (`ro.product.cpu.abi=armeabi-v7a`) auch auf 64-Bit-SoCs.
- **Gegenprobe gebaut** (`.mtest/`): `AndroidManifest.xml` aus dem Release-APK extrahiert, eigener AXML-Parser
  (`axml.py`) lokalisiert `uses-sdk`-Attribute präzise — `minSdkVersion` sitzt bei Offset **6448**, `targetSdkVersion`
  bei 6468 (Byte-Scan vorher war richtig, aber Raten ist unnötig). Wert 0x1c→0x18 gepatcht, per `repack.py`
  (erhält Reihenfolge + compress_type je Entry), `zipalign -f -p 4`, dann `apksigner` **über `java -jar lib/apksigner.jar`** —
  `apksigner.bat` scheitert an Leerzeichen im Pfad (`C:\...\00 PROJEKTE\...`).
  Signatur mit demselben Release-Zertifikat (Cert-SHA-256 unverändert) → als Test-APK `https://streamcaster.pages.dev/t.apk`.
- **ffmpeg-Install-Fehler endgültig erklärt**: nicht Pfad-/Quoting-Problem, sondern **cmd.exe-Limit von 8191 Zeichen**.
  `install-headers` übergibt ~100 absolute Header-Pfade in *einem* `install`-Aufruf; die Zeile wird abgeschnitten,
  das letzte Argument zerfällt → `install: target 'c:/Users/johan/s' is not a directory`.
  Fix: `cmake/InstallFFmpeg.sh` kopiert Libs + Header selbst (identisch auf allen Hosts), kein `make install` mehr.

  Nebenbefund: `RoundedCornerShape(28)`/`(20)` waren ebenfalls Prozent (28 %/20 % statt 28/20 dp) — optisch falsch.

## Sender behauptete "connected" ohne Empfänger (29.10. ~11:30)
- **Bug (vom Nutzer gemeldet):** Auf dem Handy blinkte die Code-Eingabe nur kurz auf, dann war die
  „connected"-Ansicht da, während der Fernseher „Warte auf Sender" zeigte.
- **Ursache 1:** `onStatus("ws")` wurde als „verbunden" gewertet — das heißt aber nur „mein Socket ist im
  Raum". Ein Raum nimmt einen einzelnen Sender klaglos an. `joined.peers` konnte das nicht beantworten,
  weil der Zähler den Beitretenden selbst mitzählt.
- **Ursache 2:** Der QR-Deeplink `/#join=<code>` wurde **nie aus der URL entfernt** → jedes Neuladen trat
  automatisch wieder bei, die Code-Eingabe war dauerhaft unerreichbar.
- **Ursache 3 (dabei gefunden):** `connect()` schloss den alten Socket nicht. Erneutes Verbinden aus dem
  Wartezustand → der alte Socket hielt die Sender-Rolle → `role_taken`.
- **Fix:** Protokoll um `peerPresent` erweitert (im Room als „Gegenrolle ist da" berechnet, Fallback
  `peers >= 2` für älteren Worker); im Sender `connected: boolean` → `phase: "home" | "waiting" | "connected"`;
  Wartezustand zeigt den Code groß + „Anderen Code eingeben"; `peer-left` → zurück in den Wartezustand;
  Deeplink wird konsumiert (`history.replaceState`) und mit `autoConnect` nur beim echten Deeplink verbunden.
- **Zweiter Fund: `/r/<CODE>` liefert auf Pages den *Sender*.** `_redirects` (`/r/* /r/index.html 200`) wird
  dort nicht angewandt, `/apk` (302) aber schon. Ein Reload auf dem TV hätte die Handy-Oberfläche gezeigt.
  Fix: Receiver hält den Code jetzt in `?code=` (`/r/?code=XXXXXX` ist eine echte Datei), Pfad-Segment wird
  weiter gelesen. Verifiziert: Reload behält den Raum.
- **Verifiziert:** eigener Playwright-Durchlauf 14/14 gegen Produktion, `e2e/specs/pairing.spec.ts` 5/5
  (2 neue Regression-Specs), plus echte Hardware: Sender-Chip „connected" ⇄ TV „Sender verbunden".
- **Nebenbefund (kosmetisch, offen):** Auf dem TV liegt im verbundenen Zustand der grüne Text
  „Sender verbunden" **über** der Zeile „Auf dem Handy unter … eingeben". Die Quelle hat an der Stelle nur
  ein einziges `Text` mit if/else — Ursache also nicht im Layout, sondern beim Rendern/Screenshot. Reproduzierbar
  über 3 Aufnahmen, tritt nur im verbundenen Zustand auf.
- **Ohne APK auf dem Fire TV (empirisch, Silk 118 / Chromium 118):** `/r/` läuft, Code + QR werden angezeigt;
  Capability-Probe des Silk: `rtc: true`, `mse: true`, mp4/H.264 + HEVC + VP9 „probably", HLS „maybe".
  MP4-Cast real getestet → Video lief. AirPlay gibt es dort nicht (dafür ist die APK da).
